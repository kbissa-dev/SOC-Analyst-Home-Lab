# Investigation 002 — WMI-Spawned PowerShell Execution

## Overview

In this investigation, I used Atomic Red Team to generate a controlled PowerShell process on my Windows 10 lab VM. The test caused WMI to launch PowerShell, producing Windows Security Event ID `4688`.

I searched for the event in Microsoft Sentinel, created a scheduled analytics rule to detect the behaviour and investigated the incidents generated by the rule.

The activity was authorised lab testing, so I selected **Benign Positive** when closing the incidents in Sentinel. Analytically, I assessed the activity as a benign true positive.

During testing, I also discovered that the original rule created two incidents for one event. I investigated the duplication, tuned the rule and confirmed the result with a second test.

## Lab Environment

- **Windows 10 VirtualBox VM:** `DESKTOP-58BSHCM`
- **Azure services:** Azure Arc and Azure Monitor Agent
- **Log Analytics workspace:** `law-soc-homelab`
- **SIEM:** Microsoft Sentinel
- **Atomic Red Team test:** `T1059.001-13`
- **Windows Security Event ID:** `4688`

## Step 1 — Verify Process Creation Auditing

Before running the test, I checked whether Windows was configured to record successful process-creation events.

I used:

```powershell
auditpol /get /subcategory:"Process Creation"
```

The result showed that successful Process Creation auditing was enabled. This was important because the investigation depended on Windows generating Event ID `4688`.

![Process Creation auditing enabled](screenshots/fig1-audit-policy.png)

## Step 2 — Run the Controlled Test

I ran Atomic Red Team test `T1059.001-13`. This is a controlled PowerShell command-line test that prints a unique GUID with `Write-Host`.

The GUID gave me a reliable value to search for in Windows and Sentinel.

**Evidence note:** The test was run more than once. Figure 2 shows a separate test run with GUID `a75860a1-2933-4cfb-af14-4307fe8ded87`. I do not have the Atomic Red Team screenshot for the run investigated in Steps 3 and 4. Figures 3 and 4 contain GUID `5593b8de-87a1-428c-aee9-97b1eef4470e`, showing the same execution in the local Windows event and Sentinel.

![Atomic Red Team output from a separate test run](screenshots/fig2-initial-atomic.png)

## Step 3 — Examine the Local Windows Event

I searched the local Windows Security log for the GUID and found Event ID `4688`.

The event showed:

- **New process:** `powershell.exe`
- **Parent process:** `WmiPrvSE.exe`
- **Target account:** `DESKTOP-58BSHCM\khush`
- **Command line:** `powershell.exe -NoProfile -C Write-Host <GUID>`
- **Token Elevation Type:** `%%1937`

Windows describes `%%1937` as Type 1, meaning a full token with no privileges removed or groups disabled. This field describes the token assigned to the process, but it does not prove malicious privilege escalation.

![Local Event ID 4688](screenshots/fig3-local-4688.png)

## Step 4 — Correlate the Event in Sentinel

I searched the `SecurityEvent` table using the GUID:

```kql
SecurityEvent
| where TimeGenerated > ago(30m)
| where EventID == 4688
| where CommandLine contains "<GUID>"
| extend IngestedAt = ingestion_time()
| extend IngestionDelay = IngestedAt - TimeGenerated
| project TimeGenerated, IngestedAt, IngestionDelay, Computer,
          Account, TargetAccount, NewProcessName,
          ParentProcessName, CommandLine, NewProcessId
```

The Sentinel record contained the same GUID as the local Event ID `4688` record in Figure 3. It also showed the same process ancestry, account context and command line.

I calculated the delay between event generation and ingestion.

![Sentinel GUID correlation](screenshots/fig4-sentinel-correlation.png)

## Field Analysis

The `Account` field showed the computer account because the process was created through the WMI service context.

The `TargetAccount` field identified my lab user account.

`WmiPrvSE.exe` as a parent process is neither malicious nor benign by itself. WMI is used by legitimate administration and monitoring tools, but attackers can also misuse it to launch processes.

The command line, identity, source and follow-on activity must therefore be examined before making a decision.

## Step 5 — Create the Analytics Rule

I created a low-severity scheduled analytics rule:

```kql
SecurityEvent
| where EventID == 4688
| where NewProcessName endswith @"\powershell.exe"
| where ParentProcessName endswith @"\WmiPrvSE.exe"
| project TimeGenerated, Computer, Account, TargetAccount,
          NewProcessName, ParentProcessName,
          CommandLine, NewProcessId
```

The rule was configured with:

- **Severity:** Low
- **Run frequency:** 5 minutes
- **Lookback period:** 10 minutes
- **Alert threshold:** More than 0 results
- **Event grouping:** One alert for each event
- **Incident creation:** Enabled
- **Host entity:** `Computer`
- **Account entity:** `TargetAccount`

I selected Low severity because this parent-child process relationship can occur during legitimate administration.

The rule identifies behaviour that requires investigation. It does not by itself prove malicious activity.

## Duplicate-Incident Finding

The detection rule created Incidents 1 and 2 for the same event. Both incidents contained the same GUID, account, host, command line and event timestamp.

![Duplicate incidents](screenshots/fig5-duplicate-incidents.png)

I determined that the duplication was caused by the rule schedule:

- The rule ran every five minutes.
- Each rule run examined the previous ten minutes.
- The same event remained inside two consecutive query windows.

This taught me that a detection rule must be tested for duplicate alerts, not only checked to see whether it fires.

## Rule Tuning

I kept the ten-minute lookback to tolerate ingestion delays, but added an ingestion-time condition:

```kql
SecurityEvent
| where EventID == 4688
| where ingestion_time() > ago(5m)
| where NewProcessName endswith @"\powershell.exe"
| where ParentProcessName endswith @"\WmiPrvSE.exe"
| project TimeGenerated, Computer, Account, TargetAccount,
          NewProcessName, ParentProcessName,
          CommandLine, NewProcessId
```

The scheduled rule continued to examine the last ten minutes of data, but the `ingestion_time()` condition restricted each execution to records ingested during the most recent five minutes.

This prevented duplicate processing during my controlled test. However, a production rule could miss an event if the rule execution was delayed or the event was ingested unusually late.

In a production environment, the timing would need to be tested using measured ingestion delays and monitored for reliability.

![Tuned analytics rule](screenshots/fig6-tuned-rule.png)

## MITRE ATT&CK Mapping

- **T1059.001 — PowerShell:** Directly supported because PowerShell executed with a command-line parameter.
- **T1047 — Windows Management Instrumentation:** `WmiPrvSE.exe` as the parent process provides WMI-related evidence.

The event does not by itself prove malicious use of WMI.

In this controlled test, WMI was used as part of the Atomic Red Team test harness. ATT&CK mapping describes the behaviour observed in the evidence; it does not prove malicious intent.

## Assessment and Disposition

**Analytical classification:** Benign true positive  
**Sentinel closure option:** Benign Positive  
**Containment:** Not required

The rule correctly detected its intended behaviour, so this was not a false positive.

However, the activity was authorised Atomic Red Team testing, and the command only printed a GUID. I found no encoded command, download activity, security-control tampering, credential access, persistence or unexpected network activity.

## Limitations

Figure 2 and Figures 3–4 contain different GUIDs and therefore do not document one continuous execution chain.

Figures 3 and 4 correlate with each other using GUID `5593b8de-87a1-428c-aee9-97b1eef4470e`. The matching Atomic Red Team console output for that execution was not retained in the published evidence.

The `ingestion_time() > ago(5m)` condition prevented duplicate processing during the controlled validation test. It may not account for every possible production delay or unusually late ingestion.

The investigation was conducted in an authorised home lab and does not demonstrate experience operating this rule in a production environment.

## Lessons Learned

- A suspicious-looking parent process is an investigation lead, not a verdict.
- A true detection can still represent benign activity.
- `TimeGenerated` and `ingestion_time()` answer different questions.
- A unique GUID can provide strong correlation when the same GUID appears across the evidence.
- Different GUIDs must not be presented as one execution.
- Detection validation should check for both missed events and duplicate alerts.
- Rule tuning should consider late ingestion and execution delays.
- ATT&CK mapping describes behaviour and does not prove malicious intent.
